## 5. ฐานข้อมูลเบอร์ชุมชน (Community Reports)

**ข้อมูลบนเซิร์ฟเวอร์** (Firestore):
- `numbers/{hash}`: จำนวนรายงาน scam / spam + เวลาอัปเดตล่าสุด
- `numbers/{hash}/reports/{uid}`: ประเภท + หมวด + เวลา — อ่านได้เฉพาะเจ้าของรายงาน
- `users/{uid}`: ตัวนับรายงานของวัน

**กันการใช้ผิด / ใส่ร้ายเบอร์คนอื่น** (บังคับใน `firebase/firestore.rules`):
- 1 บัญชีรายงาน 1 เบอร์ได้ครั้งเดียว · วันละไม่เกิน 20 รายงาน · ตัวนับเพิ่มได้ทีละ 1 พร้อมรายงานจริงเท่านั้น
- แอปจะเตือนผู้อื่นเมื่อมีผู้รายงาน **≥ 3 บัญชี** (`CallerCheck.COMMUNITY_THRESHOLD`)
- App Check (Play Integrity) ต้องเปิด enforcement สำหรับ Firestore ก่อนเปิดตัว
- รายงานชุมชน **ไม่ทำให้ตัดสาย** แค่เตือน (P7)

**การดูแลข้อมูล (ผู้ดูแลระบบ):**
- คำขอถอดเบอร์จากเจ้าของเบอร์: ตรวจหลักฐาน แล้วลบ `numbers/{hash}` และ subcollection ภายใน 7 วัน บันทึกคำขอไว้
- ทุก 3 เดือน: ลบเอกสาร `numbers` ที่ `updatedAt` เก่ากว่า 12 เดือน (เบอร์ถูกเปลี่ยนมือได้) และลบ `users` ที่ไม่ใช้งานเกิน 30 วัน
  🔜 ทำอัตโนมัติด้วย Firestore TTL policy หรือ Cloud Function เมื่อย้ายไปแพ็ก Blaze
- ห้ามดาวน์โหลด/ส่งต่อข้อมูลรายงานไปใช้นอกวัตถุประสงค์การเตือนมิจฉาชีพ
- ผู้มีสิทธิ์เข้า Firebase Console: เจ้าของโปรเจกต์เท่านั้น เปิด 2-Step Verification บังคับ

## 6. ข้อมูลเทรน

### 6.1 ข้อมูลจากข่าว (`ml/data/Dataset9_news.csv`)
- เรียบเรียงใหม่เป็นบทสนทนาจากรูปแบบที่ข่าว/หน่วยงานรายงาน **ห้ามคัดลอกเนื้อข่าว** (ลิขสิทธิ์)
- ทุกแถวมีคอลัมน์ `source` = ลิงก์ข่าวต้นทาง หรือ `synthetic-hard-negative` สำหรับสายจริงที่ทีมเขียนขึ้น
- ห้ามใส่ชื่อ เบอร์ เลขบัญชีของบุคคลจริงที่ปรากฏในข่าว
- ทุกครั้งที่เพิ่มรูปแบบมิจฉาชีพ ให้เพิ่ม "สายจริงที่คล้ายกัน" ด้วย เพื่อไม่ให้แอปเตือนผิดบ่อยขึ้น
- รอบการอัปเดต: ทุกเดือน จาก AOC 1441, ดีอี, ตำรวจไซเบอร์/CIB, ธปท., กสทช., สำนักข่าวหลัก

### 6.2 ข้อมูลจากผู้ใช้ (Data Contribution)
1. ผู้ใช้ **ยืนยันเอง** ว่าเป็นมิจฉาชีพหรือไม่
2. ข้อความผ่าน `PiiRedactor` แล้วผู้ใช้ **ตรวจ/แก้** อีกรอบ
3. ส่งออก CSV เมื่อ **ผู้ใช้กดเอง**
4. ฝั่งทีม: วางที่ `ml/data/contributed/` (**อยู่ใน .gitignore ห้ามขึ้น repo**) · ตรวจด้วยตาก่อนเทรน · ลบไฟล์ต้นฉบับภายใน 90 วันหลังรวมเข้าชุดข้อมูลหลัก · บันทึกว่าได้รับจากใคร เมื่อไหร่ เพื่อลบได้ถ้าเจ้าของขอ

## 7. การพัฒนาอย่างปลอดภัย (Secure Development)

- **กุญแจเซ็นแอป** และ `firebase.properties`: ห้ามขึ้น repo · ใช้ **Play App Signing**
  - ยกเว้น `android/app/debug.keystore` (รหัส `android`) ซึ่งเป็นกุญแจ**ทดสอบ**ที่ตั้งใจเปิดเผย เพื่อให้ APK debug ทุกรุ่นติดตั้งทับกันได้ — ห้ามใช้เซ็นรุ่นที่ขึ้น Play เด็ดขาด
- **ทุกการเปลี่ยนแปลงผ่าน Pull Request** และมีคนรีวิว โดยเช็กลิสต์:
  - [ ] ไม่เพิ่มสิทธิ์ใหม่ / ไม่เพิ่มการส่งข้อมูลขึ้นเครือข่าย (ถ้าเพิ่ม ต้องแก้นโยบายนี้ + PRIVACY_POLICY + เพิ่ม `CURRENT_CONSENT_VERSION` ใน PR เดียวกัน)
  - [ ] ไม่ log ข้อความบทสนทนา / เบอร์โทร / hash ของเบอร์
  - [ ] ข้อมูลใหม่ที่บันทึก อยู่ในตารางข้อ 2 พร้อมระยะเวลาเก็บ
  - [ ] แก้ `firebase/firestore.rules` แล้วทดสอบใน Rules Playground / Emulator ก่อน publish
  - [ ] unit test ผ่าน
  - [ ] ถ้าแก้ Entity ของ Room: เพิ่ม version + migration และ commit `android/app/schemas/` (ห้ามล้างข้อมูลผู้ใช้)
- **ไลบรารี**: เฉพาะ Google Maven / Maven Central · อัปเดตทุก 3 เดือน · ห้าม SDK โฆษณา/analytics
- **โมเดล AI**: `scam_model.json` สร้างจาก `ml/export_model.py` เท่านั้น (ตรวจความตรงกับ scikit-learn ทุกครั้ง)

## 9. ความเสี่ยงที่ยอมรับไว้ (Known Limitations)

| ความเสี่ยง | การจัดการ |
|-----------|-----------|
| AI / รายงานชุมชนผิดพลาด | เป็นแค่การเตือน ไม่ตัดสายเอง + แสดงคำแนะนำ "วางสายแล้วโทรกลับเบอร์ทางการ" |
| hash ของเบอร์ย้อนกลับได้ (เบอร์มีแค่ ~10 หลัก) | แจ้งผู้ใช้ตรง ๆ ว่าเป็นข้อมูลแฝง · ไม่เปิดให้อ่านรายงานรายคน |
| บัญชีนิรนามหลายบัญชีปั่นรายงาน | App Check + เกณฑ์ ≥ 3 + จำกัดรายวัน + ช่องทางขอถอด |
| ค่ายมือถือไทยอาจยังไม่ส่งผล STIR/SHAKEN | ถ้าไม่มีผล ระบบได้ค่า UNKNOWN และไม่กระทบการทำงานอื่น |
| มิจฉาชีพปลอมเบอร์ที่ดูปกติ | ตรวจเนื้อหาด้วย AI หลังวางสาย แล้วเตือนว่า "เบอร์อาจถูกปลอม" ถ้าเนื้อหาเสี่ยงแต่เบอร์ดูปกติ |
| `PiiRedactor` ลบชื่อคนไม่ได้ | ผู้ใช้ตรวจก่อนยืนยัน + ทีมตรวจซ้ำก่อนเทรน |
| ฐานข้อมูลในเครื่องไม่เข้ารหัสแยก | อาศัย FBE + sandbox ของ Android · พิจารณา SQLCipher ภายหลัง |
| อัปเดตแอปแล้วข้อมูลผู้ใช้หาย | ไม่ใช้ destructive migration (ยกเว้น v1 ที่ไม่เคยปล่อย) · schema ทุกเวอร์ชันอยู่ใน repo · CI fail ถ้าโครงสร้างเปลี่ยนแต่ไม่ commit schema · ขาด migration = แอป crash แทนการลบข้อมูลเงียบ ๆ |
| ข้อมูลรายงานเก่าไม่หมดอายุอัตโนมัติ (แพ็กฟรี) | ผู้ดูแลลบตามรอบในข้อ 5 |
